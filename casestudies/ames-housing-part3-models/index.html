Ames Housing - Part 3 - Closing the deal - Building Models

Dec 27, 2016 case studies

Other posts in this series:

  • Ames Housing - Part 1 - Laying the foundation - Building a Data Pipeline
  • Ames Housing - Part 2 - Walkthrough - An Exploratory Data Analysis

In Part 1, we built a data pipeline that cleans the Ames Housing dataset, and in Part 2, we explored the finalized dataset.

In this post, we build linear and non-linear models, and we find out how well they predict the SalePrice of properties. A model is a formula that a computer learns from examples. A linear model adds up the features, each multiplied by a number (a coefficient) that it learns from the data. A non-linear model can also learn curved relationships.

Evaluation Criteria

To measure how good a model is, we use the root mean squared error (RMSE) between the log of the predicted price and the log of the actual SalePrice. RMSE is the typical size of a prediction error, so a lower RMSE is better. We use the log of the prices so that an error of 10% counts the same for an expensive house and for a cheap house.

Steps for Building Models

Each model has settings that it cannot learn from the data. We must choose them before training. These settings are called hyperparameters. To choose the best hyperparameters, we use K-fold cross validation, as described in the steps below:

  • Remove features that repeat the information of other features, and change ordinal features into scores.
  • Split the training data into K parts (folds). Each time, the model learns from all the folds except one (the training part), and we check its predictions on the remaining fold (the validation part). We split the data in a way that keeps a similar mix of prices in each fold (stratified sampling).
  • Choose the linear and non-linear models to use.
  • For each model, make a set (a grid) of hyperparameter combinations that covers the possible values evenly (a space-filling grid). For glmnet, we use a regular grid, for a reason that we explain below.
  • For each combination, train the model on the training part and make predictions on the validation part. To save time, we use racing: after the first 3 folds, we drop the combinations that are clearly worse than the best one (by a statistical test), and only the others go on to the remaining folds.
  • Calculate the RMSE, and choose the combination with the lowest RMSE.
  • Train each model again, with its best combination, on the complete training set.
  • Calculate the RMSE of each final model on the testing set, which has properties that the models have not seen.
  • Choose the model with the lowest RMSE.

Removing Collinear Predictors

Many features in this dataset describe the same thing in different ways. Also, some of the features that we created in Part 1 repeat others. A model cannot use categories directly, so each category becomes a separate feature with the values 0 and 1 (a dummy variable). After this change, some features are exact combinations of other features (we call them collinear). A linear model cannot separate the effects of collinear features. So its coefficients become unreliable, or it cannot calculate them at all, and lm (the basic linear model in R) gives a warning about a “rank-deficient fit”. Models that use decision trees are not affected by repeated information. But if we remove it, the linear models work correctly and all the models are simpler.

The association matrix in Part 1 showed which features repeat each other. We drop these features, because other features already give their information:

  • HasGarage, HasFireplace and HasMasVnr are the same as, or almost the same as, the None category of GarageType, FireplaceQu and MasVnrType.
  • MSSubClass combines the type and the style of a building. BldgType and HouseStyle already give this information. Its duplex category is identical to the duplex category of BldgType.
  • TotalBath is exactly FullBath + 0.5 * HalfBath + BsmtBath. We drop HalfBath, not TotalBath. So we keep the total, which is one of the most important features for the decision tree models. And we lose no information, because we can calculate HalfBath from the other three features.

Encoding Ordinal Features

The categories of features such as OverallQual or KitchenQual have a natural order. These are ordinal features. By default, step_dummy() changes an ordinal feature into several features called polynomial contrasts. It makes one new feature for each category except one, and these features describe straight, curved and more complex trends across the grades. But some grades are very rare. For example, only one property has an OverallCond of 1. So a rare grade can be missing from a fold. Then some of these new features become collinear in that fold.

Instead, we change each ordinal feature into one whole number (a score) that follows the order of its categories: 1, 2, 3 and so on. This assumes that the steps between the grades are equal. First, we drop the categories that no property has, such as a Poor exterior quality, so that the scores have no gaps. Here are the results of a linear model with each method, on the same folds:

  • With polynomial contrasts, lm cannot calculate all the coefficients in 4 of the 5 folds. With scores, this problem happens in 0 folds.
  • With scores, the number of features goes down from 214 to 151, and the cross validated RMSE of lm goes down from 0.147 to 0.134. The simpler method works better on new data, because the model does not have to learn a separate effect for each rare grade.

Finally, step_lincomb() checks whether any features are still exact combinations of other features. This could happen because properties without a basement or a garage have the None category in every basement or garage feature. With scores, it finds no such features.

Regularized Linear Model

Next, we use glmnet, a linear model with regularization. Regularization adds a penalty for large coefficients. This makes the model keep only the effects that the data clearly supports. glmnet combines two types of regularization: LASSO (L1), which can reduce the coefficient of a feature to exactly 0, and Ridge (L2), which makes all the coefficients smaller. We search for the values of these hyperparameters that give the lowest RMSE:

  • penalty: the total amount of regularization in the model.
  • mixture: the share of LASSO (L1) regularization in the model.

We use a regular grid of 20 penalties for each of 5 mixtures, so 100 combinations. For each mixture, glmnet calculates the coefficients for the whole sequence of penalties in one fit. So the 100 combinations need only 5 fits for each fold.

Non-linear Models

Next, we train two types of models that use decision trees. A decision tree predicts a value by asking a series of yes/no questions about the features, such as “Is TotalSF more than 2000?”. These models are not very sensitive to outliers and skewed data.

ranger (Random Forest)

A random forest builds many decision trees, each from a random sample of the data, and takes the average of their predictions. We use ranger, a version of random forests that gives the same results as the randomForest package but runs about 3 times faster. Each forest has 500 trees. (On a dataset of this size, more trees do not improve the error.) We search for the best values of these hyperparameters:

  • mtry: the number of features that the tree chooses from at random at each question (split).
  • min_n: the minimum number of properties that a group (node) must have before the tree can split it again.

We search mtry between 20 and 80 of the 151 features. In an earlier search over all the possible values, smaller and larger values of mtry gave worse results, and a larger mtry also makes the training slower.

xgboost

xgboost (gradient boosting) builds decision trees one after the other. Each new tree corrects some of the errors of the trees before it. Each model has 1000 trees, and we search for the best values of these hyperparameters:

  • min_n: the minimum number of properties that a group (node) must have before the tree can split it again.
  • tree_depth: the maximum number of questions (splits) from the top of a tree to its bottom.
  • learn_rate: how much each new tree can change the predictions. A smaller value makes the model learn more slowly and carefully.

Finalizing Models

For each model, we now know the hyperparameters with the lowest RMSE. We use them to train each model again on the complete training set. Then we use the trained models to predict log(SalePrice) for the training set, and we compare the predictions with the actual values.

get_predicted <- function(model_final, dfNew) {

  # Predict on testing set
  vEstimates <- model_final %>%
    predict(new_data = dfNew) %>%
    pull(.pred)
  
  return(vEstimates)
}

New Property Premium

Of the 10 most important features in our final model, most do not change during the life of a property, such as the area, the neighborhood and the number of bathrooms. The quality and the condition of a property can change, but people judge them in different ways. The only feature that clearly changes over time is PropertyAge.

So, how does the predicted SalePrice change with the age of a property? We compare the same property when it is new, when it is more than 30 years old, and at all the ages in between.

Appendix: Tuning Code

This is the code that tunes the models. It takes several minutes, so it does not run each time we build this page. Instead, the page saves the results in the file Ames_Tuning.Rda, together with a fingerprint (a hash) of the inputs of the tuning. The inputs are the clean data from Part 1 and the tuning code itself, which also sets the hyperparameter grids. When we build the page again, it calculates the fingerprint again:

  • If the fingerprint is the same, the page loads the saved results in a few seconds.
  • If the data, a hyperparameter or any other part of the tuning code has changed, the page tunes the models again and saves the new results.

Changes to the comments or the spacing of the code do not count as changes. To tune the models again without any change, delete Ames_Tuning.Rda.

These are the tuning steps:

# Why the tuning code is built the way it is (speed):
# The dataset is small (1,460 rows x ~150 predictors after encoding), so run time is driven by the
# number of model fits (5 models x 25 grid points x 5 folds) and by how expensive each fit is, not by data size.
# The first version took ~35 minutes. Changes 1-4 brought it to ~10 minutes with 6 workers, tuning the same models
# and hyperparameters (with randomForest replaced by the equivalent ranger engine), and change 5 to ~5 minutes
# (see "Run time" below). The changes:
#   1. tune_grid() parallelises over every fold x grid-point combination ("everything"), instead of a manual
#      for-loop over grid points that only ran the 5 folds in parallel and left the remaining cores idle.
#   2. Random forest uses only the `ranger` engine with 500 trees. The `randomForest` package was tuned in addition
#      to ranger and gave the same cross-validated RMSE (0.135 vs 0.134). On one fold with mtry = 84, min_n = 2:
#        randomForest, 1,000 trees: 46.9s, RMSE 0.1305
#        ranger,       1,000 trees: 15.1s, RMSE 0.1303
#        ranger,         500 trees:  7.2s, RMSE 0.1293
#      Random forest error levels off well before 500 trees on data of this size, so 1,000 trees only doubled the cost.
#   3. xgboost searches a sensible learning-rate range, instead of spending much of the grid on learning rates as
#      small as 1e-10 that cannot converge in 1,000 rounds (see get_model_param_grid). Early stopping was tried and
#      rejected; see the note in get_model_spec.
#   4. The number of parallel workers is capped by available RAM as well as CPU cores (see "Parallel backend").
#   5. The hyperparameters are tuned by racing (finetune::tune_race_anova), not by fitting every combination on every
#      fold: after 3 of the 5 folds, combinations that are clearly worse than the best are dropped (see "Cross
#      Validation Results"). glmnet gets a regular grid that costs 5 fits per fold for 100 combinations, and ranger's
#      mtry is limited to 20-80 (see get_model_param_grid). These changes come from the Bank Marketing case study.
#
# Run time of changes 1-4: the 5 cross validations took 8.5 minutes with 6 workers (lm 1s, glmnet 13s, kernlab 42s,
# ranger 4.7 minutes, xgboost 3 minutes), and rendering the page with a new tuning run took ~10 minutes.
# With change 5 they took 4.2 minutes with 6 workers (lm 1s, glmnet 10s, kernlab 28s, ranger 1.7 minutes, xgboost
# 1.9 minutes), and the render took 5.1 minutes. Racing dropped 89 of the 100 glmnet combinations, 23 of the 25 kernlab,
# 23 of the 25 ranger and 17 of the 25 xgboost combinations. It kept the same best kernlab and xgboost combinations,
# and the best cross validated RMSE of each model stayed the same or improved (glmnet 0.129 -> 0.128, ranger 0.132,
# kernlab 0.129, xgboost 0.125). All R processes together peaked at 3.7 GB.
#
# Unrelated to speed: the earlier version used Id as a predictor. It is now excluded (see get_workflow).
# It also had 21 predictors that were exact linear combinations of others, which lm reported as a rank-deficient
# fit. They are now removed (see "Collinear predictors" and get_preprocessing_recipe), leaving a full-rank design.
# Ordered factors are encoded as integer scores instead of polynomial contrasts (see get_preprocessing_recipe).

# load the clean dataset from Part 1 (ames_data_file is set in the "tuning_cache" chunk)
load(ames_data_file)

# Collinear predictors
########################################################################################################################################################
# With the earlier set of features, 21 of the ~250 predictors were exact linear combinations of others (the design
# matrix had rank 229 of 250), so lm could not estimate them and warned of a rank-deficient fit. Tree models are not
# affected by duplicated information, but linear models are: the coefficients of collinear predictors are unstable.
# These features are dropped because other features already carry their information (see the association matrix
# in Part 1):
#   HasGarage, HasFireplace, HasMasVnr: the same as the "None" category of GarageType, FireplaceQu and MasVnrType.
#   MSSubClass: combines the building type and style, already in BldgType and HouseStyle (bias-corrected Cramer's V
#               of 0.89 and 0.83). Its "duplex" category is identical to BldgType's.
#   HalfBath:   TotalBath = FullBath + 0.5 * HalfBath + BsmtBath exactly. Dropping HalfBath rather than TotalBath
#               keeps the total, one of the most important features for the tree models, and loses no information
#               because HalfBath can be recovered from the other three.
vFeaturesCollinear <- c("HasGarage", "HasFireplace", "HasMasVnr", "MSSubClass", "HalfBath")

# Categories that no property has (e.g. a Poor exterior quality) are dropped too, so that the scores of ordered factors
# are consecutive (see get_preprocessing_recipe).
dfClean <- dfClean %>%
    select(-all_of(vFeaturesCollinear)) %>%
    mutate(across(where(is.factor), droplevels))

# Determine skewed features
vFeaturesSkew <- dfClean %>%
    select_if(is.numeric) %>%
    select_if(function(Z) abs(timeDate::skewness(Z, na.rm = T)) > 0.75) %>%
    colnames() %>%
    setdiff(c("Id","PropertyAge"))

# Remove Outliers and split clean data
########################################################################################################################################################
# dfClean <- dfClean %>% dplyr::filter(!(Id %in% c(524, 1299))) # glmnet cv_rmse improves to 0.117 but test_rmse is 0.135
dfTrain <- dfClean %>% filter(!(Id %in% vTestIDs))
dfTest <- dfClean %>% filter(Id %in% vTestIDs)

# Preprocessing Recipe
########################################################################################################################################################
# Ordered factors (quality and condition grades, etc.) are encoded as integer scores, one predictor per feature, in
# the order of their categories. The alternative, step_dummy's polynomial contrasts, creates one predictor per category
# but one. Grades that only a handful of properties have can then be missing from a cross validation fold, which makes
# the highest-order contrasts collinear: with that encoding lm reported a rank-deficient fit in 4 of the 5 folds. Scores
# assume the grades are equally spaced, which is a reasonable approximation for these grades, and they cut the
# number of predictors from ~214 to ~151. dfEncodingComparison below compares the two encodings.
#
# step_lincomb removes any remaining exact linear combinations among the predictors. These can arise because properties
# without a basement or garage share the "None" category of every basement or garage feature. An intercept column is
# added for the check, because such combinations can include a constant, and removed afterwards.
get_preprocessing_recipe <- function(df, ordinalScores = TRUE) {

    preprocessing_recipe <- recipe(SalePrice ~ ., data = df) %>%
        update_role(Id, new_role = "ID") %>%
        step_mutate_at(one_of(vFeaturesSkew), -all_outcomes(), fn = ~ log(. + 1L))
    if(ordinalScores) {
        preprocessing_recipe <- preprocessing_recipe %>%
            step_ordinalscore(all_ordered_predictors())
    }
    preprocessing_recipe <- preprocessing_recipe %>%
        step_dummy(all_nominal()) %>%
        step_intercept() %>%
        step_lincomb(all_numeric_predictors()) %>%
        step_rm(any_of("intercept")) %>%
        step_log(all_outcomes()) %>%
        prep()
    return(preprocessing_recipe)
}

# The recipe is prepared on the training set only, and the same recipe is applied to the testing set (and to any new
# data), so that both have exactly the same predictors.
preprocessing_recipe <- get_preprocessing_recipe(dfTrain)

# Preprocessed data for training models
dfTrain_Proc <- preprocessing_recipe %>%
    bake(new_data = NULL) %>%
    rename(target = SalePrice) %>%
    select(target, everything())

dfTest_Proc <- preprocessing_recipe %>%
    bake(new_data = dfTest) %>%
    rename(target = SalePrice) %>%
    select(target, everything())


# Create cv folds
########################################################################################################################################################
get_cv_folds <- function(df, numFolds, strataVar, randomSeed, shuffleData) {
    # shuffle the rows
    if(shuffleData) {
        set.seed(randomSeed)
        df <- df[sample(nrow(df)), ]
    }

    # split dataset into folds where each fold has the same distribution of target
    lFolds <- df %>% vfold_cv(v = numFolds, strata = all_of(strataVar))
    return(lFolds)
}


# Parsnip Model Specification
########################################################################################################################################################
get_model_spec <- function(modelType) {

    model_spec <- switch(modelType,
                         lm = linear_reg(mode = "regression") %>%
                             set_engine("lm"),

                         glmnet = linear_reg(mode = "regression", penalty = tune(), mixture = tune()) %>%
                             set_engine("glmnet"),

                         # No early stopping. It was tried (stop after 50 rounds without improvement on a 10% validation split)
                         # and roughly halved xgboost tuning time, but the final model was unstable: refitting the same best
                         # parameters with different random validation splits stopped anywhere from 195 to 687 rounds, with test
                         # RMSE between 0.133 and 0.151, versus 0.131 for a fixed 1,000 trees. With only ~146 validation rows the
                         # stopping point is too noisy. The narrower learn_rate range already removes the wasted fits.
                         # nthread = 1 because parallelism comes from running many fits at once (one per worker).
                         xgboost = boost_tree(mode="regression", trees=1000, min_n=tune(), tree_depth=tune(), learn_rate=tune()) %>%
                             set_engine("xgboost", objective = "reg:squarederror", nthread = 1),

                         kernlab = svm_rbf(mode="regression", cost=tune(), rbf_sigma=tune(), margin=tune()) %>%
                             set_engine("kernlab"),

                         # ranger replaces the randomForest engine: same algorithm, ~3x faster implementation, and 500 trees
                         # instead of 1,000 with no loss of accuracy (see the timings at the top of this code).
                         # num.threads = 1 for the same reason as xgboost's nthread above.
                         ranger = rand_forest(mode = "regression", trees = 500, mtry = tune(), min_n = tune()) %>%
                             set_engine("ranger", num.threads = 1))

    return(model_spec)
}


# Parameter Grid Search
########################################################################################################################################################
get_model_param_grid <- function(df, modelType, numParams, randomSeed) {

    # glmnet gets a regular grid: 20 penalties for each of 5 mixtures. glmnet calculates the coefficients for a whole
    # sequence of penalties in one fit, and tune uses this when the grid has several penalties for the same mixture
    # (penalty is a "submodel" parameter). So 100 combinations need only 5 fits per fold, while the 25-point
    # space-filling grid, with a different mixture in every point, needed 25.
    if(modelType == "glmnet") {
        return(grid_regular(penalty(), mixture(), levels = c(penalty = 20, mixture = 5)))
    }

    set.seed(randomSeed)
    param_spec <- switch(modelType,
                         kernlab = parameters(cost(), rbf_sigma(), svm_margin()),
                         # learn_rate is on a log10 scale. The dials default (1e-10 to 1e-1) spends most of the grid on rates
                         # so small that 1,000 trees barely move from the starting prediction: those fits take the full time
                         # and are never competitive. 10^-2.5 to 10^-0.5 (~0.003 to ~0.3) covers the useful range; the best
                         # rate found with the default range was ~0.07, comfortably inside it.
                         xgboost = parameters(min_n(), tree_depth(), learn_rate(range = c(-2.5, -0.5))),
                         # mtry is limited to 20-80 of the ~151 predictors. The time of a fit grows with mtry, and neither
                         # end of the full range wins. In a run over the full range (1-151), the 5 best combinations had
                         # mtry 22 to 81; all those with mtry 21 or less, or 94 or more, ranked 12th or lower. On one fold,
                         # with 500 trees and min_n = 5: mtry 10 took 1.3s (RMSE 0.137), mtry 20 3.2s (0.131), mtry 50
                         # 5.0s (0.131), mtry 90 7.7s (0.135) and mtry 150 12.4s (0.142).
                         ranger = parameters(min_n(), mtry(range = c(20, 80))))

    dfParamGrid <- grid_space_filling(param_spec, size = numParams, type = "max_entropy")
    return(dfParamGrid)
}


# Workflow for a model
########################################################################################################################################################
# The data is already preprocessed, so the workflow only names the outcome and predictors.
# Id is excluded from the predictors: it is a row identifier, and with training Ids 1-1460 and test Ids 1461-2919,
# tree models would otherwise split on it and treat every test property as lying beyond the training range.
get_workflow <- function(model_spec) {
    workflow() %>%
        add_variables(outcomes = target, predictors = -Id) %>%
        add_model(model_spec)
}


# Cross Validation Results
########################################################################################################################################################
# Racing (finetune::tune_race_anova): every combination is first fitted on 3 folds (the burn-in). Then a statistical
# test (ANOVA) on the RMSE drops the combinations that are clearly worse than the best one, and only the remaining
# combinations are fitted on the next fold, and so on. With parallel_over = "everything", each (fold, combination) fit
# is a separate task, so all workers stay busy.
# The results have one row per combination, with the mean RMSE over the folds that it completed. The combinations
# that completed all the folds come first, lowest RMSE first; the dropped ones follow.
cross_validate_model <- function(cv_folds, model_spec, param_grid) {

    tune_results <- get_workflow(model_spec) %>%
        finetune::tune_race_anova(resamples = cv_folds,
                                  grid = param_grid,
                                  metrics = metric_set(rmse),
                                  control = finetune::control_race(burn_in = 3, parallel_over = "everything"))

    # all_configs = TRUE keeps the dropped combinations, which collect_metrics() leaves out of race results by default
    dfResults <- tune_results %>%
        collect_metrics(all_configs = TRUE) %>%
        select(all_of(names(param_grid)), mean_rmse = mean, folds = n) %>%
        arrange(desc(folds), mean_rmse)
    return(dfResults)
}


# Fitted model with parameters
########################################################################################################################################################
# Returns a fitted workflow; predict() on it selects the predictor columns from new data, so Id can stay in the data.
# The seed makes the final ranger and xgboost fits reproducible between runs.
get_fitted_model <- function(df, model_spec, dfParams, randomSeed = 2300) {

    model_wf <- get_workflow(model_spec)
    if(!is.null(dfParams)) model_wf <- model_wf %>% finalize_workflow(dfParams)
    set.seed(randomSeed)
    fit(model_wf, data = df)
}


# Parallel backend
########################################################################################################################################################
# Each worker is a separate R session with tidymodels and the model packages loaded. In a full run with 5 workers,
# no R process exceeded 0.6 GB and all R processes together (main session + workers) peaked at 3.2 GB. Budgeting
# 0.75 GB per worker leaves headroom. Workers are capped at cores - 1 (to keep the machine responsive) and at what fits in 70% of the RAM
# available when the run starts, so the run cannot push the machine into swapping even if other applications are open.
gb_per_worker <- 0.75
gb_available <- ps::ps_system_memory()$avail / 1024^3
num_workers <- max(1, min(parallel::detectCores() - 1, floor(0.7 * gb_available / gb_per_worker)))
message(sprintf("Using %d parallel workers (%.1f GB RAM available)", num_workers, gb_available))
plan(multisession, workers = num_workers)

# Compare the encodings of ordered factors with a linear model on the same folds (reported in the post)
compare_encoding <- function(ordinalScores) {

    df <- get_preprocessing_recipe(dfTrain, ordinalScores) %>%
        bake(new_data = NULL) %>%
        rename(target = SalePrice) %>%
        select(target, everything())
    folds <- get_cv_folds(df, numFolds = 5, strataVar = "target", randomSeed = 2300, shuffleData = T)
    vAliased <- map_int(folds$splits, ~ sum(is.na(coef(lm(target ~ ., data = analysis(.x) %>% select(-Id))))))

    tibble(encoding = if(ordinalScores) "ordinal scores" else "polynomial contrasts",
           predictors = ncol(df) - 2,
           folds_rank_deficient = sum(vAliased > 0),
           lm_cv_rmse = suppressWarnings(get_workflow(get_model_spec("lm")) %>%
                                             fit_resamples(resamples = folds, metrics = metric_set(rmse)) %>%
                                             collect_metrics() %>%
                                             pull(mean)))
}
dfEncodingComparison <- bind_rows(compare_encoding(ordinalScores = FALSE), compare_encoding(ordinalScores = TRUE))

# Time each model so the post can report relative run times
dfTimings <- tibble(model = character(), seconds = numeric())
time_model <- function(model, expr) {
    t0 <- Sys.time()
    result <- force(expr)
    dfTimings <<- dfTimings %>% add_row(model = model, seconds = as.numeric(difftime(Sys.time(), t0, units = "secs")))
    result
}

# The clean dataset from Part 1
ames_data_file <- "../ames-housing-part1-data-pipeline/Ames_Housing_Clean.Rda"

# Fingerprint (hash) of the inputs of the tuning: the data that it uses, and the code of the "tuning_steps"
# chunk, which also sets the hyperparameter grids. Comments and spacing are removed from the code first, so
# editing them does not start a new tuning run.
envData <- new.env()
load(ames_data_file, envir = envData)
tuning_steps <- knitr::knit_code$get("tuning_steps")
tuning_hash <- rlang::hash(list(data = list(envData$dfClean, envData$vTestIDs),
                                code = deparse(parse(text = tuning_steps, keep.source = FALSE))))

# If the saved results were made from the same inputs, load them. Otherwise, tune the models again and save
# the new results together with the fingerprint of their inputs.
envSaved <- new.env()
if (file.exists("Ames_Tuning.Rda")) load("Ames_Tuning.Rda", envir = envSaved)
if (identical(envSaved$tuning_hash, tuning_hash)) {
  list2env(as.list(envSaved), envir = environment())
} else {
  eval(parse(text = tuning_steps))
  save(list = c(vTuningResults, "tuning_hash"), file = "Ames_Tuning.Rda")
}
rm(envData, envSaved)
