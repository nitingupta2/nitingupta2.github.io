Bank Marketing - Part 3 - Keeping up with the times - Sliding and Expanding Window Models

Oct 18, 2026 case studies

Other posts in this series:

  • Bank Marketing - Part 1 - Making the call - An Exploratory Data Analysis
  • Bank Marketing - Part 2 - Who will say yes? - Building Classification Models

In Part 1, we found that the subscription rate changed a lot between 2008 and 2010, as interest rates fell and the bank changed its campaigns. In Part 2, we built models on a random sample of the calls and tested them on the other calls from the same period. They did well. But when we trained them on the earlier calls and tested them on the later calls, they did much worse.

The calls in this dataset are independent of each other: one client’s answer does not change another client’s answer. But they are not independent of time. What makes a client say yes, and how often, depends on the economy and on the campaign at the time. A model learned from the past only works for the near future.

So in this post, we do what a bank would do in practice. We take the calls of the past months, choose the hyperparameters and train the models on them, and use the models to predict the calls of the next 3 months, which the models have never seen. Then we move forward by 3 months, and repeat. This is called a walk-forward evaluation. We compare two ways of choosing the past months:

  • A sliding window of the last 12 months, which forgets the older months.
  • An expanding window of all the months so far, which keeps everything.

How the Windows Work

Each cycle has two parts:

  • A training window of past months. We choose the hyperparameters with cross validation on these calls only, and train the final model on all of them.
  • A testing period of the next 3 months. The model predicts these calls, which it has never seen.

Then we move forward by 3 months. The first testing period starts in June 2009, the first month with 12 full months of calls before it, and the last one ends in November 2010, the last month of the data. The two kinds of windows use the same testing periods:

  • The sliding window is the 12 calendar months before the testing period. Some months have no calls, so a window can have fewer than 12 months of calls.
  • The expanding window starts with the same 12 months, and keeps all the months since then. So in the first cycle, the two windows are the same, and the first cycle is run only once.

What’s notable?

  • The sliding windows shrink from 28,452 calls in the first cycle to 2,665 in the last, because the bank made fewer calls each year. The expanding windows grow, but only to 32,779, because the later months have few calls.
  • The subscription rate in the sliding windows rises from 7.7% to 49.3%, close to the rates of the testing periods. In the expanding windows, it only reaches 12.5%, because most of their calls are always from 2008, when few clients said yes.
  • Cycle 3 tests only December 2009, because there were no calls in January and February 2010.

In each cycle, the code checks that every training call was made before every testing call, and that no call is in both. Everything that the model learns, including the hyperparameters and the preparation of the features (such as the dummy variables and which features are skewed), comes from the training window only.

Feature Sets

We compare three sets of features:

  • client and campaign: the features of the client and of the call, such as age, job, contact, month and the history of previous campaigns. No economic features.
  • + economic levels: the same features plus the five economic features, as in Part 2.
  • + economic trends: the client and campaign features plus three features that describe how things changed, instead of their levels: euribor_change, the change of the Euribor rate; employed_change, the change of the number of employees; and prev_month_rate, the subscription rate in the last month that the model knows.

For the calls in a testing period, the trend features compare with the last month of the training window, the last month that the bank knows when it trains the model. So the model does not use the results of other calls in the testing period.

What’s notable?

  • On calls that they have not seen, from the next 3 months, all the models do much worse than in Part 2: their ROC AUC is between 0.573 and 0.659, compared with about 0.80 on the random testing set of Part 2. The best is glmnet with the client and campaign features and the expanding window, with 0.659, just ahead of the same model with the sliding window (0.655).
  • Within a month, the sliding windows rank the clients better: the average ROC AUC within a month is higher with the sliding window for 5 of the 6 combinations of model and features.
  • The economic features do not help, with either kind of window. With their levels, glmnet has the worst log loss, because it predicts far too many subscribers in some months.
  • Without the economic features, the models expect far fewer subscribers than there are, and more so with the expanding window: an average predicted probability of 22% with the expanding window and 27% with the sliding window for glmnet, compared with the actual rate of 44%.

  • Within a month, which is what matters to decide whom to call, the sliding window is better for 5 of the 6 combinations.

So in this dataset, forgetting the old past helps. An expanding window would be the better choice when the past stays relevant, or when there is too little recent data. A middle way, which we have not tried here, is to keep all the past calls but give the recent calls more weight.

With Perfect Foresight

In Part 2, we chose the hyperparameters by cross validation on a random sample of the calls of the whole period, including the calls that we predict here. So those hyperparameters were chosen with knowledge of the future (perfect foresight), which a bank never has. How much better would the models do with them?

Here, we train the models in every cycle with the hyperparameters of Part 2, without tuning, on the same training windows, and test them on the same testing periods. For glmnet, they are a penalty of 1e-10 and a mixture of 1. For xgboost, they are min_n = 23, tree_depth = 4 and learn_rate = 0.0254.

What’s notable?

  • The hyperparameters chosen with perfect foresight do not make the models better. Over all the testing periods together, they give a higher ROC AUC for only 5 of the 12 combinations of window, model and features, and the average difference is +0.001 (from -0.010 to +0.018).
  • Within a month, they are better for 5 of the 12 combinations, and slightly worse on average (-0.004).
  • So the large difference between Part 2 (a ROC AUC of about 0.80) and this post (about 0.65) does not come from the hyperparameters. It comes from the data: in Part 2, the models learned from calls of the same months as the calls that they predicted. Knowing the future hyperparameters is worth almost nothing; knowing the future clients is worth a lot.
  • The models are not very sensitive to the exact hyperparameters here. Choosing them again in each cycle mainly protects us from a lookahead: it costs much more time (about 61 minutes for all the cycles, compared with 3 minutes to train the models with fixed hyperparameters), but it is the only choice that a bank could make in practice.

Comparison with Part 2

The three ways of testing the models give very different answers:

  • On a random testing set from the same period (Part 2), the best models had a ROC AUC of about 0.80.
  • When we trained on the first 75% of the calls and tested on the last 25% (Part 2), the ROC AUC was between 0.28 and 0.71, depending on the model and the features. But the hyperparameters had been chosen on calls from the whole period.
  • With sliding and expanding windows, where every choice is made on past calls only, the ROC AUC over all the testing periods is between 0.573 and 0.659.

The testing periods are not exactly the same (the later calls of Part 2 start in May 2009, and the testing periods here start in June 2009), so the numbers cannot be compared exactly. But the message is clear: the random testing set of Part 2 gave a much too good picture of how the models would predict future calls. And as we saw above, the hyperparameters of Part 2, chosen with perfect foresight, explain almost none of the difference.

How a Bank Could Use the Models

Even with modest ROC AUCs, the models are useful within a month. If the bank calls the 20% of each month’s clients with the highest probabilities, using the glmnet model with the client and campaign features and the expanding window:

dfTopCalls <- dfWindowPred %>%
  filter(window == best_row$window, model == best_row$model, feature_set == best_row$feature_set) %>%
  group_by(year_month) %>%
  arrange(desc(.pred_yes), .by_group = TRUE) %>%
  mutate(called = row_number() <= ceiling(0.2 * n())) %>%
  ungroup()

top_reach <- sum(dfTopCalls$y == "yes" & dfTopCalls$called) / sum(dfTopCalls$y == "yes")
top_rate <- mean(dfTopCalls$y[dfTopCalls$called] == "yes")
all_rate <- mean(dfTopCalls$y == "yes")
  • It reaches 31% of the subscribers with 20% of the calls.
  • 68% of these calls end with a yes, compared with 44% of all the calls in the testing periods: 1.5 times as many.

This is a smaller gain than in Part 2, where the top 20% reached about two thirds of the subscribers. But it is an honest estimate of what the bank could expect from a model trained on the past.

Conclusions

  • When the data covers a period of time, the way we test a model matters as much as the model itself. A random testing set lets the model learn from the same period that it is tested on, and it gives a much too good picture.
  • In a walk-forward evaluation, every step that learns from data, including the choice of the hyperparameters, the preparation of the features and the features that describe the recent past, must use the training window only. Then the testing period is truly unseen.
  • On truly unseen calls, the models rank the clients within a month moderately well, and calling the top 20% of each month gives about 1.5 times the success rate of calling at random.
  • The economic features, which looked so useful in Part 2, do not help a model that predicts the future: the economy of the next months is outside what the model has seen.
  • Even the hyperparameters of Part 2, chosen with perfect foresight, do not make the models better. The models of Part 2 looked good because they learned from the same months that they were tested on, not because of their hyperparameters.
  • When the behavior of the clients changes over time, a sliding window of recent months adapts faster than an expanding window of all the past months, ranks the clients within a month better, and costs less to train. In practice, a bank should train its models again often, on recent calls, and watch how well they predict each new month.

This code runs the sliding and expanding windows. It takes more than an hour, so it does not run each time we build this page. Instead, the page saves the results in the file Bank_Windows.Rda, together with a fingerprint (a hash) of the inputs: the clean data from Part 1 and the code itself. When we build the page again, it calculates the fingerprint again:

  • If the fingerprint is the same, the page loads the saved results in a few seconds.

These steps prepare the data, the features, the cycles and the models:

# How the window code is built:
#   1. Each cycle has a training window and a testing period of the next 3 months, and the next cycle starts 3 months
#      later. Two kinds of training windows are compared on the same testing periods:
#        sliding:   the 12 calendar months before the testing period.
#        expanding: all the months from the first usable month (June 2008) to the month before the testing period.
#                   It starts with the same 12 months as the sliding window, and grows by 3 months in each cycle.
#      Hyperparameters are tuned within each training window only, so no information from the testing period or later
#      is used (no lookahead). The Part 2 hyperparameters are not reused, because they were tuned on calls from the
#      whole period.
#   2. Within a training window, the hyperparameters are tuned by racing with 5-fold cross validation, as in Part 2.
#      The folds are random within the window: they do not need to respect time, because all of them come before the
#      testing period.
#   3. Three feature sets are compared: the client and campaign features only, these plus the five economic features
#      (their levels, as in Part 2), and these plus three trend features that describe how the economy and the campaign
#      changed (see "Trend features").
#   4. Two models are compared: glmnet (regularized logistic regression) and xgboost. Plain logistic regression is not
#      used, because the later training windows have only a few thousand calls and ~50 predictors, where an
#      unregularized model is unstable. ranger is not used, because it was the slowest to tune in Part 2, and it did
#      not do better than xgboost.
#   5. The cycles run one after another; within a cycle, the tuning runs in parallel (see "Parallel backend").
#   6. A cycle whose training window and testing period are the same as those of an earlier cycle is not run again:
#      its results are reused. This is the case for the first cycle, where both windows are the same 12 months.

# load the clean dataset and the dates of the calls from Part 1 (bank_data_file is set in the "window_cache" chunk)
load(bank_data_file)

dfCalls <- dfClean %>%
    inner_join(dfCallDates, by = "Id") %>%
    arrange(Id)

# Trend features
########################################################################################################################################################
# Calculated from past months only:
#   euribor_change:  the 3 month Euribor on the day of the call, minus its average in a reference month.
#   employed_change: the number of employees (nr.employed) at the time of the call, minus its average in the
#                    reference month.
#   prev_month_rate: the subscription rate in the reference month.
# For the calls in a training window, the reference month is the previous month with calls (some months have no calls:
# January, February and September 2008). For the calls in a testing period, it is the last month of the training
# window, for all 3 testing months (see "Run the cycles"). Otherwise, in the 2nd and 3rd testing months,
# prev_month_rate would use the results of calls in the testing period, which the model must not see.
# Euribor and employment on the day of a call are published economic data, known at the time of the call.
# The first month, May 2008, has no previous month, so its calls are left out.
dfMonthly <- dfCalls %>%
    group_by(year_month) %>%
    summarise(calls = n(), rate = mean(y == "yes"), euribor_mean = mean(euribor3m), employed_mean = mean(nr.employed)) %>%
    arrange(year_month) %>%
    mutate(prev_euribor = lag(euribor_mean), prev_employed = lag(employed_mean), prev_month_rate = lag(rate))

dfCalls <- dfCalls %>%
    inner_join(dfMonthly %>% select(year_month, prev_euribor, prev_employed, prev_month_rate), by = "year_month") %>%
    mutate(euribor_change = euribor3m - prev_euribor,
           employed_change = nr.employed - prev_employed) %>%
    select(-prev_euribor, -prev_employed) %>%
    filter(!is.na(prev_month_rate))

vFeaturesEconomic <- c("emp.var.rate", "cons.price.idx", "cons.conf.idx", "euribor3m", "nr.employed")
vFeaturesTrend <- c("euribor_change", "employed_change", "prev_month_rate")

# predictors left out of each feature set (Id, year and year_month are never predictors)
lFeatureSets <- list("client and campaign" = c(vFeaturesEconomic, vFeaturesTrend),
                     "+ economic levels" = vFeaturesTrend,
                     "+ economic trends" = vFeaturesEconomic)


# Cycles
########################################################################################################################################################
# The first testing period starts 12 calendar months after the first usable month (June 2008), so that every training
# window has at least 12 full months. Each cycle tests the next 3 months, and the next cycle starts 3 months later,
# until the last month of the data. Both kinds of windows use the same testing periods.
first_month <- min(dfCalls$year_month)
last_month <- max(dfCalls$year_month)
dfTestPeriods <- tibble(test_start = seq(first_month %m+% months(12), last_month, by = "3 months")) %>%
    mutate(cycle = row_number(), test_end = test_start %m+% months(2))
dfCycles <- bind_rows(sliding = dfTestPeriods %>% mutate(train_start = test_start %m-% months(12)),
                      expanding = dfTestPeriods %>% mutate(train_start = first_month),
                      .id = "window") %>%
    mutate(train_end = test_start %m-% months(1),
           train_first = as.Date(NA), train_last = as.Date(NA), test_first = as.Date(NA), test_last = as.Date(NA),
           train_calls = NA_integer_, train_rate = NA_real_, test_calls = NA_integer_, test_rate = NA_real_)

# Preprocessing Recipe
########################################################################################################################################################
# As in Part 2: dummy variables, log of right-skewed features, and removal of single-value predictors and exact linear
# combinations. It is prepared on the training window of each cycle only, and so is the choice of the skewed features.
vFeaturesClientNum <- c("age", "campaign", "previous")
get_preprocessing_recipe <- function(df) {

    vFeaturesSkew <- df %>%
        select(all_of(vFeaturesClientNum)) %>%
        select_if(function(Z) timeDate::skewness(Z, na.rm = T) > 0.75) %>%
        colnames()

    recipe(y ~ ., data = df) %>%
        update_role(Id, year, year_month, new_role = "ID") %>%
        step_mutate_at(all_of(vFeaturesSkew), fn = ~ log(. + 1)) %>%
        step_dummy(all_nominal_predictors()) %>%
        step_zv(all_predictors()) %>%
        step_intercept() %>%
        step_lincomb(all_numeric_predictors()) %>%
        step_rm(any_of("intercept")) %>%
        prep()
}

# Models and grids
########################################################################################################################################################
class_metrics <- metric_set(roc_auc, pr_auc, mn_log_loss)

get_model_spec <- function(modelType) {
    switch(modelType,
           glmnet = logistic_reg(mode = "classification", penalty = tune(), mixture = tune()) %>%
               set_engine("glmnet"),
           xgboost = boost_tree(mode = "classification", trees = 1000, min_n = tune(), tree_depth = tune(),
                                learn_rate = tune()) %>%
               set_engine("xgboost", nthread = 1))
}

# The same grids as in Part 2 (glmnet: 20 penalties x 5 mixtures; xgboost: a space-filling grid over the same ranges),
# with 10 instead of 25 xgboost combinations, because the tuning runs 18 times (6 cycles x 3 feature sets). In a test
# run with 4 xgboost combinations, xgboost already took 9 minutes over the 18 tuning runs. The ranges are not narrowed
# with what Part 2 found, because Part 2 tuned on calls from the whole period (that would be a lookahead).
get_model_param_grid <- function(modelType, randomSeed = 2300) {
    if(modelType == "glmnet") {
        return(grid_regular(penalty(), mixture(), levels = c(penalty = 20, mixture = 5)))
    }
    set.seed(randomSeed)
    grid_space_filling(parameters(min_n(), tree_depth(), learn_rate(range = c(-2.5, -0.5))), size = 10, type = "max_entropy")
}

# !! puts the names in vExclude into the workflow itself. Without it, the workflow keeps a reference to the variable,
# which the parallel workers cannot find.
get_workflow <- function(model_spec, vExclude) {
    workflow() %>%
        add_variables(outcomes = y, predictors = c(-Id, -year, -year_month, -any_of(!!vExclude))) %>%
        add_model(model_spec)
}

# Tune a model on the training window with racing, train it with the best combination on the whole window, and
# predict the testing period
tune_fit_predict <- function(dfTrain_Proc, dfTest_Proc, modelType, vExclude, randomSeed = 2300) {

    model_spec <- get_model_spec(modelType)
    set.seed(randomSeed)
    folds <- vfold_cv(dfTrain_Proc, v = 5, strata = y)
    race <- get_workflow(model_spec, vExclude) %>%
        finetune::tune_race_anova(resamples = folds,
                                  grid = get_model_param_grid(modelType, randomSeed),
                                  metrics = class_metrics,
                                  control = finetune::control_race(burn_in = 3, parallel_over = "everything"))
    params_best <- select_best(race, metric = "roc_auc")
    set.seed(randomSeed)
    model_final <- get_workflow(model_spec, vExclude) %>%
        finalize_workflow(params_best) %>%
        fit(data = dfTrain_Proc)

    list(params = params_best %>% select(-.config),
         cv_roc_auc = show_best(race, metric = "roc_auc", n = 1)$mean,
         predictions = dfTest_Proc %>%
             select(Id, year_month, y) %>%
             mutate(.pred_yes = predict(model_final, dfTest_Proc, type = "prob")$.pred_yes))
}

These steps run the cycles of both kinds of windows:

# Run the cycles
########################################################################################################################################################
lResults <- list()
lDone <- list()     # results of each training window and testing period that has been run, to reuse them
dfTimings <- tibble(window = character(), cycle = integer(), model = character(), feature_set = character(),
                    seconds = numeric(), reused = logical())
for (i in seq_len(nrow(dfCycles))) {

    cycle <- dfCycles[i, ]
    cycle_key <- paste(cycle$train_start, cycle$train_end, cycle$test_start, cycle$test_end)
    dfTrain <- dfCalls %>% filter(year_month >= cycle$train_start, year_month <= cycle$train_end)
    dfTest <- dfCalls %>% filter(year_month >= cycle$test_start, year_month <= cycle$test_end)

    # The testing period must be unseen: every training call comes before every testing call, and no call is in both
    stopifnot(max(dfTrain$year_month) < min(dfTest$year_month),
              length(intersect(dfTrain$Id, dfTest$Id)) == 0)

    # Trend features of the testing calls, relative to the last month of the training window (see "Trend features")
    reference_month <- dfMonthly %>% filter(year_month == max(dfTrain$year_month))
    dfTest <- dfTest %>%
        mutate(euribor_change = euribor3m - reference_month$euribor_mean,
               employed_change = nr.employed - reference_month$employed_mean,
               prev_month_rate = reference_month$rate)

    preprocessing_recipe <- get_preprocessing_recipe(dfTrain)
    dfTrain_Proc <- bake(preprocessing_recipe, new_data = NULL)
    dfTest_Proc <- bake(preprocessing_recipe, new_data = dfTest)

    for (feature_set in names(lFeatureSets)) {
        for (modelType in c("glmnet", "xgboost")) {
            task_key <- paste(cycle_key, feature_set, modelType)
            reused <- !is.null(lDone[[task_key]])
            t0 <- Sys.time()
            if (!reused) {
                lDone[[task_key]] <- tune_fit_predict(dfTrain_Proc, dfTest_Proc, modelType, lFeatureSets[[feature_set]])
            }
            result <- lDone[[task_key]]
            dfTimings <- dfTimings %>% add_row(window = cycle$window, cycle = cycle$cycle, model = modelType,
                                               feature_set = feature_set, reused = reused,
                                               seconds = as.numeric(difftime(Sys.time(), t0, units = "secs")))
            lResults[[length(lResults) + 1]] <- list(window = cycle$window, cycle = cycle$cycle, model = modelType,
                                                     feature_set = feature_set, params = result$params,
                                                     cv_roc_auc = result$cv_roc_auc, predictions = result$predictions)
        }
    }
    dfCycles$train_first[i] <- min(dfTrain$year_month)
    dfCycles$train_last[i] <- max(dfTrain$year_month)
    dfCycles$test_first[i] <- min(dfTest$year_month)
    dfCycles$test_last[i] <- max(dfTest$year_month)
    dfCycles$train_calls[i] <- nrow(dfTrain)
    dfCycles$train_rate[i] <- mean(dfTrain$y == "yes")
    dfCycles$test_calls[i] <- nrow(dfTest)
    dfCycles$test_rate[i] <- mean(dfTest$y == "yes")
}

Perfect Foresight Code

This code trains the models with the hyperparameters chosen in Part 2, in every cycle of both kinds of windows. It uses the data, the features, the cycles and the functions of the steps above. Its results are saved in Bank_Foresight.Rda, with their own fingerprint, which also includes the hyperparameters of Part 2.

# Perfect foresight: the hyperparameters chosen in Part 2
########################################################################################################################################################
# Part 2 chose the hyperparameters by cross validation on a random sample of the calls of the whole period, including
# the testing periods here, so they were chosen with knowledge of the future (perfect foresight). Here, each model is
# trained in every cycle with those hyperparameters, without tuning, on the same training windows as above, and tested
# on the same testing periods. Part 2 tuned the models with all the features (like the "+ economic levels" set); the
# same hyperparameters are used with every feature set.
envPart2 <- new.env()
load(part2_tuning_file, envir = envPart2)
lParamsForesight <- list(glmnet = envPart2$param_best_glmnet, xgboost = envPart2$param_best_xgboost)
rm(envPart2)

# Train a model with the given hyperparameters on the training window, and predict the testing period
fit_predict_fixed <- function(dfTrain_Proc, dfTest_Proc, modelType, vExclude, params, randomSeed = 2300) {

    set.seed(randomSeed)
    model_final <- get_workflow(get_model_spec(modelType), vExclude) %>%
        finalize_workflow(params) %>%
        fit(data = dfTrain_Proc)
    dfTest_Proc %>%
        select(Id, year_month, y) %>%
        mutate(.pred_yes = predict(model_final, dfTest_Proc, type = "prob")$.pred_yes)
}

# The same steps as in "Run the cycles", with the fixed hyperparameters instead of tuning. The 6 models of a cycle
# (2 models x 3 feature sets) are trained in parallel. As above, a cycle with the same training window and testing
# period as an earlier cycle (the first cycle) reuses its results.
lForesight <- list()
lDoneForesight <- list()
dfForesightTimings <- tibble(window = character(), cycle = integer(), seconds = numeric(), reused = logical())
for (i in seq_len(nrow(dfCycles))) {

    cycle <- dfCycles[i, ]
    cycle_key <- paste(cycle$train_start, cycle$train_end, cycle$test_start, cycle$test_end)
    reused <- !is.null(lDoneForesight[[cycle_key]])
    t0 <- Sys.time()

    if (!reused) {
        dfTrain <- dfCalls %>% filter(year_month >= cycle$train_start, year_month <= cycle$train_end)
        dfTest <- dfCalls %>% filter(year_month >= cycle$test_start, year_month <= cycle$test_end)

        # The testing period must be unseen: every training call comes before every testing call, and no call is in both
        stopifnot(max(dfTrain$year_month) < min(dfTest$year_month),
                  length(intersect(dfTrain$Id, dfTest$Id)) == 0)

        # Trend features of the testing calls, relative to the last month of the training window (see "Trend features")
        reference_month <- dfMonthly %>% filter(year_month == max(dfTrain$year_month))
        dfTest <- dfTest %>%
            mutate(euribor_change = euribor3m - reference_month$euribor_mean,
                   employed_change = nr.employed - reference_month$employed_mean,
                   prev_month_rate = reference_month$rate)

        preprocessing_recipe <- get_preprocessing_recipe(dfTrain)
        dfTrain_Proc <- bake(preprocessing_recipe, new_data = NULL)
        dfTest_Proc <- bake(preprocessing_recipe, new_data = dfTest)

        dfTasks <- expand_grid(feature_set = names(lFeatureSets), model = c("glmnet", "xgboost"))
        lPred <- furrr::future_map2(dfTasks$feature_set, dfTasks$model, function(feature_set, modelType) {
            fit_predict_fixed(dfTrain_Proc, dfTest_Proc, modelType, lFeatureSets[[feature_set]],
                              lParamsForesight[[modelType]]) %>%
                mutate(feature_set = feature_set, model = modelType)
        }, .options = furrr::furrr_options(seed = TRUE, packages = c("tidymodels", "glmnet", "xgboost")))
        lDoneForesight[[cycle_key]] <- bind_rows(lPred)
    }

    dfForesightTimings <- dfForesightTimings %>%
        add_row(window = cycle$window, cycle = cycle$cycle, reused = reused,
                seconds = as.numeric(difftime(Sys.time(), t0, units = "secs")))
    lForesight[[i]] <- lDoneForesight[[cycle_key]] %>% mutate(window = cycle$window, cycle = cycle$cycle)
}
