Bank Marketing - Part 2 - Who will say yes? - Building Classification Models

Oct 18, 2026 case studies

Other posts in this series:

  • Bank Marketing - Part 1 - Making the call - An Exploratory Data Analysis

In Part 1, we explored the Bank Marketing dataset: 41,188 calls in which a Portuguese bank asked its clients to open a term deposit. Only about 1 in 9 clients said yes.

In this post, we build models that predict whether a client will subscribe. A model is a formula that a computer learns from examples. A classification model does not just answer yes or no: it gives each client a probability of saying yes. A bank can use these probabilities to call the most promising clients first.

Evaluation Criteria

In Part 1, we saw that only 11.3% of the clients subscribed. So we cannot judge a model by its accuracy, the share of correct yes/no answers: a model that always says no would be 88.7% accurate and would never find a subscriber. Instead, we judge a model by how well it ranks the clients, using its predicted probabilities:

  • ROC AUC (area under the ROC curve) is the probability that the model gives a random subscriber a higher probability than a random client who did not subscribe. 0.5 means that the model ranks clients no better than chance, and 1 means that it ranks every subscriber above every other client. This is our main measure, because a bank needs to know whom to call first.
  • PR AUC (area under the precision-recall curve) focuses on the subscribers. Precision is the share of subscribers among the clients that the model picks, and recall is the share of all the subscribers that it finds. A model that picks clients at random has a PR AUC equal to the subscription rate, 0.113. PR AUC shows differences between models that ROC AUC can hide when one class is rare.
  • Log loss measures how good the probabilities themselves are. Lower is better.

Steps for Building Models

Each model has settings that it cannot learn from the data. We must choose them before training. These settings are called hyperparameters. To choose the best hyperparameters, we use K-fold cross validation, as in the Ames Housing case study:

  • Change the categorical features into numbers that a model can use.
  • Split the training data into K parts (folds). Each time, the model learns from all the folds except one (the training part), and we check its predictions on the remaining fold (the validation part). Each fold has the same subscription rate (stratified sampling).
  • For each model, make a set (a grid) of hyperparameter combinations that covers the possible values evenly.
  • For each combination, train the model on the training part and make predictions on the validation part. To save time, we use racing: after the first 3 folds, we drop the combinations that are clearly worse than the best one (by a statistical test), and only the others go on to the remaining folds.
  • Choose the combination with the highest ROC AUC over all the folds.
  • Train each model again, with its best combination, on the complete training set.
  • Measure each final model on the testing set, which has clients that the models have not seen.

Preparing the Features

A model cannot use categories directly. So each category of a categorical feature becomes a separate feature with the values 0 and 1 (a dummy variable), except one category of each feature, which is the baseline. For example, contact becomes one feature, contact_telephone, which is 1 for a landline and 0 for a cell phone.

We also take the log of the skewed numerical features (age and campaign and previous), so that a few clients with very large values do not dominate the linear models. Models that use decision trees are not affected by this change.

The unknown categories of housing and loan are the same clients, so their dummy variables are identical. When a feature is an exact combination of other features, a linear model cannot separate their effects. step_lincomb() removes these 1 features: loan_unknown.

After these steps, there are 50 features.

Linear Models

Logistic Regression

Logistic regression is the basic linear model for classification. It adds up the features, each multiplied by a coefficient, and changes the total into a probability between 0 and 1. It has no hyperparameters, so we use it as a benchmark: more complex models are only worth it if they do better.

  • Logistic regression has a cross validated ROC AUC of 0.789 and a PR AUC of 0.446. Its PR AUC is about 4 times the 0.113 of a random ranking.
  • It takes about 21 seconds to cross validate.

Regularized Logistic Regression

We use glmnet, which adds a penalty for large coefficients to logistic regression (regularization). This helps when features repeat each other’s information, such as the economic features. We do a grid search of these hyperparameters:

  • penalty: The total amount of regularization in the model.
  • mixture: The proportion of L1 regularization (LASSO), which can set coefficients to exactly 0, versus L2 regularization (Ridge), which only shrinks them.

We try 20 penalties for each of 5 mixtures. glmnet calculates the model for a whole series of penalties at once, so this costs only one fit per mixture.

Non-linear Models

Next, we train two models that are built from decision trees. A decision tree splits the clients into groups with a series of yes/no questions, such as “Was the previous campaign a success?”. Tree models can learn curved relationships and interactions between features without our help.

ranger (Random Forest)

A random forest averages the predictions of many trees. Each tree learns from a random sample of the clients, and each split considers a random subset of the features. We use 500 trees and do a grid search of these hyperparameters:

  • mtry: The number of features to randomly sample at each split.
  • min_n: The minimum number of clients in a group required to split it further.

xgboost

Boosted trees add trees one at a time, and each new tree corrects the errors of the trees before it. We use 1,000 trees and do a grid search of these hyperparameters:

  • min_n: The minimum number of clients in a group required to split it further.
  • tree_depth: The maximum number of questions in a row in each tree.
  • learn_rate: How much each new tree changes the predictions.

What’s notable?

  • On the testing set, each model does about as well as in cross validation, so the hyperparameters were not tuned to the training data by chance.
  • The tree models are again slightly better: ranger and xgboost have a test ROC AUC of 0.803 and 0.803, and logistic regression has 0.796.

  • The ROC curves rise steeply at first: the clients with the highest probabilities are very likely to subscribe. After that, the models struggle to separate the remaining subscribers from the other clients.

How a Bank Could Use the Model

A bank cannot call every client. With a model, it can sort the clients by their predicted probability and call them from the top of the list. The gain curve shows the share of all the subscribers that the bank would reach, for each share of the clients that it calls:

dfTestPred %>%

  ggplot(aes(x = .percent_tested / 100, y = .percent_found / 100, color = model)) +

       title = "Gain curves on the testing set", subtitle = "The dashed line is calling clients in random order")

For the best model by cross validated ROC AUC, xgboost, here is what different call plans would achieve on the testing set:

dfBest <- dfTestPred %>% filter(model == best_model) %>% arrange(desc(.pred_yes))
overall_rate <- mean(dfBest$y == "yes")

dfCallPlans <- map_dfr(c(0.1, 0.2, 0.3, 0.5), function(share) {

         clients_called = nCalled,

What’s notable?

  • By calling the 10% of the clients with the highest probabilities, the bank would reach 47% of all the subscribers. 52% of these calls would end with a yes, 4.7 times the rate of calling at random.
  • Calling the top 20% reaches 66% of the subscribers. After that, each extra call finds fewer new subscribers: calling half of the clients reaches 82%.
  • The best plan depends on the cost of a call and on the value of a new deposit. The model gives the bank the list in the best order. The bank decides where to stop.

What Drives the Predictions?

The xgboost model is not as easy to read as a linear model, but it can tell us how much each feature improved its trees (the feature importance). The glmnet model is easier to read: for a categorical feature, the odds ratio of a category says how many times the odds of subscribing are multiplied for a client in that category, compared with the baseline category.

What’s notable?

  • In xgboost, nr.employed is by far the most important feature, and the other economic features follow. As we saw in Part 1, they tell the model when the call was made, and the subscription rate changed a lot over time.
  • Among the client features, the most important are the history with the bank (recent_contact, poutcome, previous), age, the number of calls in this campaign and the type of phone.
  • In glmnet, a recent contact in a previous campaign multiplies the odds of a yes by about 3.2, and a successful previous campaign by about 1.9 (compared with a failed one). A call to a landline about halves the odds.
  • Every month has lower odds than March, the baseline month, after taking the economy into account. March had the highest subscription rate in Part 1.
  • The large odds ratio of education_illiterate is not reliable, because only 18 clients have this category.

Testing on Later Calls

In Part 1, we saw that the economic features tell a model when a call was made, and that the subscription rate changed a lot over time. The testing set above has calls from the same period as the training set. But a bank would use the model to plan future calls.

So we train the best model (xgboost) again, with the same hyperparameters, on the first 75% of the calls in time order, and we test it on the last 25%. We do the same with logistic regression, the simplest model. We train each model twice: with all the features, and without the five economic features.

What’s notable?

  • The later calls are very different: 26% of them ended with a yes, compared with 6% of the earlier calls.
  • All the models do much worse on the later calls than on the random testing set. With all the features, xgboost has a ROC AUC of 0.611, compared with 0.803 on the random testing set. Without the economic features, its ROC AUC of 0.503 is no better than chance.

A linear model extends the straight-line trend that it learned, and here that trend points the wrong way.
  • Logistic regression without the economic features does best, with a ROC AUC of 0.707. In the earlier calls, only 0.4% of the clients had a successful previous campaign, compared with 12% in the later calls. The tree models saw too few of these clients to learn much from them, but logistic regression still learned one coefficient for them, and it carries over to the later calls.
  • So the random testing set gives a much too good picture of how the models would do in a future campaign. A bank should train the models again often, on its most recent calls, and test them on the calls that came after.

Conclusions

  • On calls from the same period, all the models rank the clients well, with a ROC AUC of about 0.8 on the testing set. The tree models are slightly better than logistic regression, but they take much longer to tune.
  • A bank could reach about 66% of the subscribers by calling only the top 20% of the clients on the list.
  • The strongest signals are the economy at the time of the call and the client’s history with the bank. The economic features make the models look good on a random testing set, but they do not carry over to a later period with a different economy.
  • When the data covers a period of time, a random testing set is not enough. We must also test the models on later data, which is how they will be used.

Appendix: Tuning Code

This is the code that tunes the models. It takes several minutes, so it does not run each time we build this page. Instead, the page saves the results in the file Bank_Tuning.Rda, together with a fingerprint (a hash) of the inputs of the tuning. The inputs are the clean data from Part 1 and the tuning code itself, which also sets the hyperparameter grids. When we build the page again, it calculates the fingerprint again:

  • If the fingerprint is the same, the page loads the saved results in a few seconds.
  • If the data, a hyperparameter or any other part of the tuning code has changed, the page tunes the models again and saves the new results.

Changes to the comments or the spacing of the code do not count as changes. To tune the models again without any change, delete Bank_Tuning.Rda.

These are the tuning steps:

# How the tuning code is built:
# It follows the tuning code of the Ames Housing case study (Part 3), adapted for classification:
#   1. The hyperparameters are tuned by racing (finetune::tune_race_anova), not by fitting every combination on every
#      fold: after 3 of the 5 folds, combinations that are clearly worse than the best are dropped (see "Cross
#      Validation Results"). Each (fold, combination) fit is a separate parallel task, so all workers stay busy.
#   2. The number of parallel workers is capped by available RAM as well as CPU cores (see "Parallel backend").
#   3. Models are compared by ROC AUC (see "Metrics"). Accuracy is not used: with 11% of clients subscribing, a model
#      that always predicts "no" is 89% accurate.
#   4. The models are logistic regression (the baseline, no hyperparameters), glmnet (regularized logistic regression),
#      ranger (random forest) and xgboost (boosted trees).
#      An SVM (kernlab), which the Ames case study also tuned, is not used here. Training an SVM takes time that grows
#      faster than the square of the number of rows, and each cross validation fit here has ~24,700 rows (17 times as
#      many as Ames). It also does not give class probabilities without an extra, slower calibration step.
#   5. After tuning, the best model is also trained on the earlier calls and tested on the later calls (see "Testing on
#      later calls"), because the economic features tell the model when a call was made (see Part 1). The post adds
#      logistic regression to this check outside the tuning steps, because it takes only seconds.
#
# Run time: the first version of this code fitted every combination on every fold, with mtry up to 20, a 25-point
# space-filling grid for glmnet and a 1 GB memory budget per worker (4 workers on this machine). A full run took ~28
# minutes: logistic regression 11s, glmnet 3 minutes, ranger 17 minutes and xgboost 6 minutes, plus the final fits.
# The changes in this version (racing, a regular grid for glmnet, mtry up to 10, 0.75 GB per worker) are explained
# where they are made. This version took ~17 minutes with 5 workers: logistic regression 21s (including starting the
# workers), glmnet 39s, ranger 10 minutes and xgboost 4.4 minutes, plus the final fits. Racing dropped 45 of the 100
# glmnet combinations, 11 of the 25 ranger combinations and 16 of the 25 xgboost combinations, and it kept the same
# best xgboost combination. The saving is less than the share of dropped combinations, because every combination is
# fitted on 3 of the 5 folds before any is dropped. All R processes together peaked at 4.9 GB.

# load the clean dataset from Part 1 (bank_data_file is set in the "tuning_cache" chunk)
load(bank_data_file)

# Training and testing sets (the stratified split was made in Part 1)
########################################################################################################################################################
dfTrain <- dfClean %>% filter(!(Id %in% vTestIDs))
dfTest <- dfClean %>% filter(Id %in% vTestIDs)

# Right-skewed numerical features (a long tail of large values), which are log transformed for the linear models
# (tree models are not affected by it). Only positive skewness counts: nr.employed is skewed to the left, and the log
# of an employment count would not make its distribution more even.
vFeaturesSkew <- dfClean %>%
    select(all_of(vFeaturesNum)) %>%
    select_if(function(Z) timeDate::skewness(Z, na.rm = T) > 0.75) %>%
    colnames()

# Preprocessing Recipe
########################################################################################################################################################
# Categorical features become dummy variables (one 0/1 predictor per category but one). The "unknown" categories of
# housing and loan are the same 990 clients, so those two dummy variables are identical. step_lincomb removes exact
# linear combinations like this one. An intercept column is added for the check, because such combinations can include
# a constant, and removed afterwards. step_zv removes predictors with a single value.
get_preprocessing_recipe <- function(df) {

    recipe(y ~ ., data = df) %>%
        update_role(Id, new_role = "ID") %>%
        step_mutate_at(all_of(vFeaturesSkew), fn = ~ log(. + 1)) %>%
        step_dummy(all_nominal_predictors()) %>%
        step_zv(all_predictors()) %>%
        step_intercept() %>%
        step_lincomb(all_numeric_predictors()) %>%
        step_rm(any_of("intercept")) %>%
        prep()
}

# The recipe is prepared on the training set only, and the same recipe is applied to the testing set (and to any new
# data), so that both have exactly the same predictors.
preprocessing_recipe <- get_preprocessing_recipe(dfTrain)
dfTrain_Proc <- preprocessing_recipe %>% bake(new_data = NULL)
dfTest_Proc <- preprocessing_recipe %>% bake(new_data = dfTest)


# Metrics
########################################################################################################################################################
# ROC AUC: the probability that a random subscriber gets a higher predicted probability than a random non-subscriber.
#          It measures how well the model ranks clients, which is what a bank needs to decide whom to call first.
# PR AUC:  the average precision (share of subscribers among the clients called) over all recall levels. It focuses on
#          the rare class, so it shows differences between models that ROC AUC can hide when classes are imbalanced.
# Log loss: measures how good the probabilities themselves are (lower is better).
# "yes" is the first level of y, so it is the event for all three metrics.
class_metrics <- metric_set(roc_auc, pr_auc, mn_log_loss)


# Parsnip Model Specification
########################################################################################################################################################
get_model_spec <- function(modelType) {

    model_spec <- switch(modelType,
                         glm = logistic_reg(mode = "classification") %>%
                             set_engine("glm"),

                         glmnet = logistic_reg(mode = "classification", penalty = tune(), mixture = tune()) %>%
                             set_engine("glmnet"),

                         # 500 trees, as in the Ames case study: random forest performance levels off well before that.
                         # num.threads = 1 because parallelism comes from running many fits at once (one per worker).
                         ranger = rand_forest(mode = "classification", trees = 500, mtry = tune(), min_n = tune()) %>%
                             set_engine("ranger", num.threads = 1),

                         # No early stopping, for the reason found in the Ames case study: with a random validation split,
                         # the stopping point, and so the final model, changed from one run to the next.
                         xgboost = boost_tree(mode = "classification", trees = 1000, min_n = tune(), tree_depth = tune(),
                                              learn_rate = tune()) %>%
                             set_engine("xgboost", nthread = 1))

    return(model_spec)
}


# Parameter Grid Search
########################################################################################################################################################
get_model_param_grid <- function(df, modelType, numParams, randomSeed) {

    # glmnet gets a regular grid: 20 penalties for each of 5 mixtures. glmnet calculates the coefficients for a whole
    # sequence of penalties in one fit, and tune uses this when the grid has several penalties for the same mixture
    # (penalty is a "submodel" parameter). So 100 combinations need only 5 fits per fold, while the 25-point
    # space-filling grid, with a different mixture in every point, needed 25.
    if(modelType == "glmnet") {
        return(grid_regular(penalty(), mixture(), levels = c(penalty = 20, mixture = 5)))
    }

    set.seed(randomSeed)
    param_spec <- switch(modelType,
                         # learn_rate is on a log10 scale; ~0.003 to ~0.3 covers the useful range for 1,000 trees (see the
                         # Ames case study, where the dials default spent most of the grid on rates that never converged).
                         xgboost = parameters(min_n(), tree_depth(), learn_rate(range = c(-2.5, -0.5))),
                         # mtry is limited to 1-10 of the ~50 predictors. Small values win, and the time of a fit grows with
                         # mtry. In a test run over the full range, mtry 6 and 2 had ROC AUC 0.794 and 0.793, and mtry 35-37
                         # had 0.781-0.788. On one fold, with 500 trees and min_n = 10: mtry 6 took 14.4s (ROC AUC 0.788),
                         # mtry 20 took 30.7s (0.784) and mtry 35 took 46.2s (0.780). In a full run with mtry up to 20, all
                         # 5 best combinations had mtry 2 to 7, and ranger still took 62% of the tuning time.
                         ranger = parameters(min_n(), mtry(range = c(1, 10))))

    dfParamGrid <- grid_space_filling(param_spec, size = numParams, type = "max_entropy")
    return(dfParamGrid)
}


# Workflow for a model
########################################################################################################################################################
# The data is already preprocessed, so the workflow only names the outcome and predictors.
# Id is excluded from the predictors: it is the order of the calls, so a tree model could otherwise split on it and
# learn the period of a call directly. vExclude removes more predictors (used in "Testing on later calls").
get_workflow <- function(model_spec, vExclude = character()) {
    workflow() %>%
        add_variables(outcomes = y, predictors = c(-Id, -any_of(vExclude))) %>%
        add_model(model_spec)
}


# Cross Validation Results
########################################################################################################################################################
# Racing (finetune::tune_race_anova): every combination is first fitted on 3 folds (the burn-in). Then a statistical
# test (ANOVA) on the ROC AUC, the first metric in class_metrics, drops the combinations that are clearly worse than the
# best one, and only the remaining combinations are fitted on the next fold, and so on. With parallel_over =
# "everything", each (fold, combination) fit is a separate task, so all workers stay busy.
# The results have one row per combination, with the mean of each metric over the folds that it completed. The
# combinations that completed all the folds come first, best ROC AUC first; the dropped ones follow.
cross_validate_model <- function(cv_folds, model_spec, param_grid) {

    tune_results <- get_workflow(model_spec) %>%
        finetune::tune_race_anova(resamples = cv_folds,
                                  grid = param_grid,
                                  metrics = class_metrics,
                                  control = finetune::control_race(burn_in = 3, parallel_over = "everything"))

    # all_configs = TRUE keeps the dropped combinations, which collect_metrics() leaves out of race results by default
    dfResults <- tune_results %>%
        collect_metrics(all_configs = TRUE) %>%
        select(all_of(names(param_grid)), .metric, mean, folds = n) %>%
        pivot_wider(names_from = .metric, values_from = mean) %>%
        arrange(desc(folds), desc(roc_auc))
    return(dfResults)
}


# Fitted model with parameters
########################################################################################################################################################
# Returns a fitted workflow; predict() on it selects the predictor columns from new data, so Id can stay in the data.
# The seed makes the final ranger and xgboost fits reproducible between runs.
get_fitted_model <- function(df, model_spec, dfParams, randomSeed = 2300, vExclude = character()) {

    model_wf <- get_workflow(model_spec, vExclude)
    if(!is.null(dfParams)) model_wf <- model_wf %>% finalize_workflow(dfParams)
    set.seed(randomSeed)
    fit(model_wf, data = df)
}


# Parallel backend
########################################################################################################################################################
# Each worker is a separate R session with tidymodels and the model packages loaded. The training set here is 21 times
# the size of the Ames training set, and one ranger probability forest of 500 trees takes ~150 MB. In a full run with
# 4 workers, all R processes together peaked at 3.4 GB, of which the main session (which holds the data and the final
# models) used 1.1 GB, so each worker used ~0.6 GB. Budgeting 0.75 GB per worker leaves headroom. Workers are capped
# at cores - 1 (to keep the machine responsive) and at what fits in 70% of the RAM available when the run starts, so
# the run cannot push the machine into swapping. On a CPU with 4 cores and 8 threads (hyperthreading), workers beyond
# 4 share cores, so they add less than a full core each.
gb_per_worker <- 0.75
gb_available <- ps::ps_system_memory()$avail / 1024^3
num_workers <- max(1, min(parallel::detectCores() - 1, floor(0.7 * gb_available / gb_per_worker)))
message(sprintf("Using %d parallel workers (%.1f GB RAM available)", num_workers, gb_available))
plan(multisession, workers = num_workers)

# Create cross validation folds, stratified so that each fold has the same subscription rate
set.seed(2300)
cv_folds <- vfold_cv(dfTrain_Proc, v = 5, strata = y)

# Time each model so the post can report relative run times
dfTimings <- tibble(model = character(), seconds = numeric())
time_model <- function(model, expr) {
    t0 <- Sys.time()
    result <- force(expr)
    dfTimings <<- dfTimings %>% add_row(model = model, seconds = as.numeric(difftime(Sys.time(), t0, units = "secs")))
    result
}

# logistic regression (no hyperparameters, so fit_resamples instead of tune_grid)
model_spec_glm <- get_model_spec(modelType = "glm")
cv_results_glm <- time_model("glm",
    get_workflow(model_spec_glm) %>%
        fit_resamples(resamples = cv_folds, metrics = class_metrics) %>%
        collect_metrics() %>%
        select(.metric, mean) %>%
        pivot_wider(names_from = .metric, values_from = mean))
model_final_glm <- get_fitted_model(dfTrain_Proc, model_spec_glm, NULL)

# glmnet model
model_spec_glmnet <- get_model_spec(modelType = "glmnet")
param_grid_glmnet <- get_model_param_grid(dfTrain_Proc, modelType = "glmnet", numParams = 25, randomSeed = 2300)
cv_results_glmnet <- time_model("glmnet", cross_validate_model(cv_folds, model_spec_glmnet, param_grid_glmnet))
param_best_glmnet <- cv_results_glmnet %>% slice(1) %>% select(all_of(names(param_grid_glmnet)))
model_final_glmnet <- get_fitted_model(dfTrain_Proc, model_spec_glmnet, param_best_glmnet)

# random forest model (ranger engine)
model_spec_rf <- get_model_spec(modelType = "ranger")
param_grid_rf <- get_model_param_grid(dfTrain_Proc, modelType = "ranger", numParams = 25, randomSeed = 2300)
cv_results_rf <- time_model("ranger", cross_validate_model(cv_folds, model_spec_rf, param_grid_rf))
param_best_rf <- cv_results_rf %>% slice(1) %>% select(all_of(names(param_grid_rf)))
model_final_rf <- get_fitted_model(dfTrain_Proc, model_spec_rf, param_best_rf)

# xgboost model
model_spec_xgboost <- get_model_spec(modelType = "xgboost")
param_grid_xgboost <- get_model_param_grid(dfTrain_Proc, modelType = "xgboost", numParams = 25, randomSeed = 2300)
cv_results_xgboost <- time_model("xgboost", cross_validate_model(cv_folds, model_spec_xgboost, param_grid_xgboost))
param_best_xgboost <- cv_results_xgboost %>% slice(1) %>% select(all_of(names(param_grid_xgboost)))
model_final_xgboost <- get_fitted_model(dfTrain_Proc, model_spec_xgboost, param_best_xgboost)

plan(sequential)


# Testing on later calls
########################################################################################################################################################
# The random split above tests the models on calls from the same period as the training calls. Here, the best model
# by cross validated ROC AUC is trained on the first 75% of the calls (in time order, Id) and tested on the last 25%,
# with the same hyperparameters, once with all the features and once without the five economic features.
vFeaturesEconomic <- c("emp.var.rate", "cons.price.idx", "cons.conf.idx", "euribor3m", "nr.employed")
dfAll_Proc <- bind_rows(dfTrain_Proc, dfTest_Proc) %>% arrange(Id)
idCutoff <- quantile(dfAll_Proc$Id, 0.75)
dfEarly_Proc <- dfAll_Proc %>% filter(Id <= idCutoff)
dfLate_Proc <- dfAll_Proc %>% filter(Id > idCutoff)

dfCVBest <- bind_rows(glmnet = cv_results_glmnet %>% slice(1), ranger = cv_results_rf %>% slice(1),
                      xgboost = cv_results_xgboost %>% slice(1), .id = "model")
best_model <- dfCVBest$model[which.max(dfCVBest$roc_auc)]
best_spec <- switch(best_model, glmnet = model_spec_glmnet, ranger = model_spec_rf, xgboost = model_spec_xgboost)
best_params <- switch(best_model, glmnet = param_best_glmnet, ranger = param_best_rf, xgboost = param_best_xgboost)

score_later_calls <- function(vExclude, features) {
    model_early <- get_fitted_model(dfEarly_Proc, best_spec, best_params, vExclude = vExclude)
    dfPred <- dfLate_Proc %>% select(y) %>% bind_cols(predict(model_early, dfLate_Proc, type = "prob"))
    tibble(features = features,
           roc_auc = roc_auc_vec(dfPred$y, dfPred$.pred_yes),
           pr_auc = pr_auc_vec(dfPred$y, dfPred$.pred_yes),
           mean_predicted = mean(dfPred$.pred_yes),
           actual_rate = mean(dfPred$y == "yes"))
}
dfLaterCalls <- bind_rows(score_later_calls(character(), "all features"),
                          score_later_calls(vFeaturesEconomic, "without economic features"))
dfEarlyLateRates <- tibble(period = c("earlier calls (training)", "later calls (testing)"),
                           calls = c(nrow(dfEarly_Proc), nrow(dfLate_Proc)),
                           rate = c(mean(dfEarly_Proc$y == "yes"), mean(dfLate_Proc$y == "yes")))

# The clean dataset from Part 1
bank_data_file <- "../bank-marketing-part1-eda/Bank_Marketing_Clean.Rda"

# Fingerprint (hash) of the inputs of the tuning: the data that it uses, and the code of the "tuning_steps"
# chunk, which also sets the hyperparameter grids. Comments and spacing are removed from the code first, so
# editing them does not start a new tuning run.
envData <- new.env()
load(bank_data_file, envir = envData)
tuning_steps <- knitr::knit_code$get("tuning_steps")
tuning_hash <- rlang::hash(list(data = list(envData$dfClean, envData$vTestIDs),
                                code = deparse(parse(text = tuning_steps, keep.source = FALSE))))

# If the saved results were made from the same inputs, load them. Otherwise, tune the models again and save
# the new results together with the fingerprint of their inputs.
envSaved <- new.env()
if (file.exists("Bank_Tuning.Rda")) load("Bank_Tuning.Rda", envir = envSaved)
if (identical(envSaved$tuning_hash, tuning_hash)) {
  list2env(as.list(envSaved), envir = environment())
} else {
  eval(parse(text = tuning_steps))
  save(list = c(vTuningResults, "tuning_hash"), file = "Bank_Tuning.Rda")
}
rm(envData, envSaved)
